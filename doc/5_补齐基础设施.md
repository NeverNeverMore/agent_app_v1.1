# 5_补齐基础设施

## 一、审批持久化与刷新恢复

### 保存位置

审批状态保存到 Electron 的用户数据目录：

```text
<userData>/pending-approvals.json
```

应用启动时由主进程初始化审批存储。新建审批后只持久化可序列化的审批记录，不保存 Promise、定时器或事件回调。

### 刷新恢复

渲染进程初始化会通过 `list-pending-approvals` IPC 查询主进程仍然持有的待审批记录。若记录属于当前会话，前端恢复请求关联、加载状态和审批横幅，用户可以继续点击批准或拒绝。

该机制解决的是“渲染页面刷新”场景：主进程和 Agent 循环仍然存活，因此原来的审批 Promise 仍可继续等待。

### 应用重启处理

应用重启后，原来的 Agent 循环、Promise 和事件回调已经不存在，不能伪造恢复执行。启动时会清理上一进程遗留的 pending 文件，旧审批不会继续生效，也不会让新 Agent 误执行文件写入。

审批仍保留 5 分钟 TTL。过期、批准、拒绝、取消后都会从 pending 存储中移除，并向前端发送终态事件。

## 二、符号链接越界安全

### 原有问题

旧实现只比较字符串形式的绝对路径。项目目录内的符号链接或 Windows junction 可能指向项目外部，导致 `file_read`、`file_list` 或受限模式下的 `file_write` 间接访问工作区之外的内容。

### 修复方式

新增 `electron/tools/pathSecurity.ts`：

- 已存在的读取/列表目标使用 `fs.realpath` 校验真实路径；
- 新写入目标向上查找最近的已存在父目录，并校验父目录真实路径；
- 已存在的写入目标也会再次 realpath 校验，防止目标文件本身是外部链接；
- 真实路径必须位于项目根目录或其子目录，否则返回“路径越界”。

因此普通 `../`、符号链接、junction 和链接文件都会受到统一保护。

### ask/full 边界

- `ask` 模式：`file_read`、`file_list` 和 `file_write` 继续受关联项目目录限制；`file_write` 还需要审批。
- `full` 模式：按已确认的产品规则，`file_write` 允许绝对路径及项目目录外路径，因此不套用项目根目录限制；但仍保留参数校验、内容大小限制、目录目标拒绝和执行错误处理。
- `dangerous` 工具仍然拒绝，不会因 full 模式自动开放。

## 五、当前限制与后续方向

1. 审批持久化用于页面刷新和状态查询，不是跨进程 Agent 任务恢复。应用完全重启后，旧审批会被取消清理。
2. full 模式允许本地任意文件路径写入，这是产品明确选择的高风险能力，建议后续增加更显眼的风险提示、审计日志和可选的路径白名单。
3. 当前项目没有互联网工具，因此权限文案中的互联网访问属于未来能力预留。
4. 后续可继续增加审批历史审计、跨窗口同步和更完整的集成测试。
