本文档根据当前 `agent_app_v1.1` 项目代码、项目 `doc` 目录文档、参考 PPT，以及 OpenViking 官方项目和 `OpenViking介绍.md` 整理形成。

## 三、产品概述

令旗是一个本地优先的桌面 Agent 工作台，以 Electron 桌面客户端承载聊天、文件分析、工具执行、权限审批和任务状态管理。

它解决的不是“再做一个聊天窗口”，而是把用户正在处理的本地文件、项目目录、企业知识和受控工具连接起来，让 Agent 在明确的权限边界内完成连续工作。

### 3.1 当前项目已实现能力

- Electron + React + TypeScript 桌面客户端；
- OpenAI 兼容协议和 Anthropic 协议接入；
- SSE 流式回复、停止生成、失败重试和联通性检测；
- 多会话、项目目录关联和本地会话持久化；
- TXT、MD、CSV、JSON、PDF、DOCX、XLSX、PPTX、图片和代码文件分析；
- 内置时间、计算、目录、文件读写和 HTTP 读取工具；
- 工具参数校验、超时、取消、错误码和结果截断；
- `ask` / `full` 权限模式及写文件审批；
- 路径越界和符号链接越界防护；
- 任务状态、错误恢复和待审批状态刷新恢复；
- 基础 MCP Client 和 Skill 管理能力。

### 3.2 OpenViking 接入状态

当前代码中还没有 OpenViking Server 客户端、资源导入接口或统一的共享知识空间。PPT 和本文档中的 OpenViking 内容，是下一阶段的架构设计，不应理解为当前版本已经完成的功能。

## 四、OpenViking 的正确定位

OpenViking 是面向 AI Agent 的开源上下文数据库（Context Database）。它统一管理：

- **Resources**：项目文档、代码、网页、图片和其他业务资料；
- **Memories**：用户偏好、长期记忆和 Agent 经验；
- **Skills**：可复用的技能、规则和工作方法。

它不是聊天机器人，也不是令旗客户端本身。它更像一个供多个 Agent 使用的上下文基础设施，提供资源导入、目录浏览、语义检索、分层读取和长期记忆能力。

OpenViking 使用 `viking://` 虚拟文件系统组织内容：

```text
viking://
├── resources/              # 组织共享资源
└── user/<user_id>/
    ├── memories/           # 用户个人记忆
    ├── resources/           # 用户私有资源
    └── skills/              # 用户或项目技能
```

每项内容可以按三层加载：

- **L0 Abstract**：一句话摘要，用于快速判断是否相关；
- **L1 Overview**：概要和结构，用于规划下一步；
- **L2 Details**：完整原文，只在真正需要时读取。

这样可以减少无关上下文进入模型，降低 Token 消耗，并保留目录浏览轨迹，便于调试检索结果。

## 五、推荐总体架构：中心共享 + 用户隔离

### 5.1 核心结论

OpenViking 建议作为独立服务运行，拥有自己的服务进程和端口。开发或单机体验时，默认可以使用：

```text
http://127.0.0.1:1933
```

`1933` 是常见示例端口，实际部署应以服务配置为准。生产环境不应把该端口直接暴露到公网，而应放在企业内网、VPN 或 HTTPS 反向代理之后，并配合身份认证和资源权限。

### 5.2 推荐部署形态

| 形态 | 说明 | 适用场景 |
|---|---|---|
| 中心共享服务 | 内网部署一个 OpenViking Server，多个令旗客户端通过 HTTP/SDK 访问。 | 企业团队、部门知识库、多人协作。 |
| 本地伴随服务 | 安装包同时提供 OpenViking Server，桌面端启动独立进程并访问本机端口。 | 单人使用、离线场景、开发调试。 |
| 混合模式（推荐） | 中心服务保存组织知识；客户端保留本地缓存和个人临时资料。 | 既需要共享，又需要个人隐私和离线容错。 |

这里的“本地伴随服务”仍然是独立进程，不是把 OpenViking 的内部存储模块直接编译进 Electron。这样可以降低桌面端耦合，也方便未来将服务迁移到企业服务器。

### 5.3 分层职责

```text
多个令旗桌面客户端
  负责聊天界面、文件选择、Agent 编排、权限审批和结果展示
          ↓ IPC
令旗主进程 / Agent Orchestrator
  负责模型请求、任务状态、工具调用、上下文拼装和访问策略
          ↓ HTTP / SDK（必要时 MCP）
OpenViking Server
  负责共享资源、目录结构、语义检索、分层读取和长期记忆
          ↓
资源存储与索引
  AGFS / VikingFS 内容层 + Vector Index 向量索引层
```

## 六、共享知识与个人数据边界

“大家都可以上传，大家都可以使用”需要建立在资源分类和权限控制之上，不应让所有用户无条件写入所有内容。

### 6.1 组织共享资源

适合放入公共资源空间的内容包括公司制度、产品手册、公共流程、已发布项目文档、标准模板和经过审核的知识材料。它们可供多个用户检索和阅读。

### 6.2 部门或项目资源

财务、审计、研发、法务和项目资料通常需要按部门、项目或角色授权。用户可以发现自己有权限的目录，但不应通过客户端绕过原有业务系统权限。

### 6.3 用户个人空间

用户偏好、个人工作习惯、未发布草稿和个人 Agent 经验应进入 `user/<user_id>/memories` 或用户私有资源目录，默认不与其他用户共享。

### 6.4 Skills 的位置

Skill 作为可选的文本规则，可以有组织级、部门级、项目级和个人级版本。它不应被当成知识库的替代品，也不应拥有独立的文件执行权限。

一个建议的目录结构如下：

```text
viking://resources/
├── company/                # 公司公开制度和标准资料
├── departments/            # 部门授权资料
├── projects/               # 项目资料
└── published/              # 已审核发布内容

viking://user/<user_id>/
├── memories/               # 个人长期记忆
├── resources/              # 个人资料
└── skills/                 # 个人规则
```

## 七、知识上传与发布流程

推荐将“上传文件”和“发布为共享知识”拆成两个动作：

```text
用户选择文件
  → 客户端校验类型、大小和敏感级别
  → 上传到待处理区
  → 服务解析文本、生成摘要和索引
  → 进入待审核或待发布状态
  → 管理员/负责人确认目录、标签和权限
  → 发布到共享资源空间
  → 其他用户按权限检索和读取
```

导入资源时，OpenViking 可以自动解析内容、生成摘要、调用 Embedding 模型并建立索引。对于项目文档和代码，建议以目录或批量任务导入，不建议用户通过 UI 一条一条录入。

生产环境建议增加以下治理字段：

- 资源所属组织、部门和项目；
- 资源负责人和审核人；
- 数据敏感级别和保密期限；
- 生效时间、更新时间和废弃状态；
- 允许访问的用户组或角色；
- 原始文件位置、版本号和内容哈希。

## 八、令旗与 OpenViking 的接入方式

### 8.1 推荐访问链路

```text
React 渲染进程
  → Electron Preload 白名单 API
  → Electron 主进程 / Agent Orchestrator
  → OpenVikingClient
  → OpenViking Server
```

渲染进程不直接访问 OpenViking，也不直接持有服务端认证信息。所有访问都经过主进程的服务封装和权限策略。

### 8.2 建议封装的客户端能力

在 Electron 主进程中新增 `OpenVikingClient` 或同等服务层，统一处理：

- `health`：服务健康检查和启动状态；
- `add_resource`：导入项目文档、代码和业务资料；
- `find` / `search`：根据用户任务召回相关上下文；
- `read`：按命中的 URI 读取 L0、L1 或 L2 内容；
- `remember` 或 session API：保存可共享或个人范围的长期记忆；
- 认证、超时、重试、错误转换和访问日志。

### 8.3 HTTP、SDK 和 MCP 的取舍

- **HTTP / SDK**：适合令旗自己严格控制调用顺序，推荐作为主入口；
- **MCP**：适合让模型自主决定何时搜索、读取或保存记忆，可作为可选工具入口；
- 两种方式可以共存，但同一个操作最好只有一个主入口，避免重复导入、重复召回或重复写入。

## 九、结合 Agent 的工作流程

接入 OpenViking 后，一次典型任务可以这样执行：

```text
用户提出任务
  → Agent 判断是否需要共享知识或历史记忆
  → OpenViking 召回相关目录和摘要
  → Agent 按需读取 L1 或 L2 详细内容
  → 将必要上下文交给模型
  → 模型决定是否调用本地工具或外部业务工具
  → 工具执行前进行权限检查和必要审批
  → 结果回写当前会话
  → 可选：提交会话并抽取长期记忆
```

OpenViking 负责“找到和组织上下文”，令旗负责“理解任务、编排工具、执行权限和展示结果”。两者职责清晰，便于独立升级。

## 十、与当前项目的对应关系

| 领域 | 当前项目已有能力 | OpenViking 接入后的变化 |
|---|---|---|
| 对话 | React Chat + Electron 主进程流式请求。 | 在请求前增加共享上下文召回和按需读取。 |
| 会话 | localStorage 保存本地会话。 | 可选提交会话，抽取组织记忆或个人记忆。 |
| 文件 | 本地附件解析，任务结束后清理临时文件。 | 经审核的文件可异步导入共享资源空间。 |
| 工具 | ToolRegistry、执行器、超时、取消和权限分级。 | OpenViking 检索能力可封装为主进程服务或可选工具。 |
| 权限 | `ask` / `full`，写文件有审批。 | 增加用户、部门、项目和资源访问权限校验。 |
| MCP | 当前支持本地 `stdio` MCP Server。 | 可选连接 OpenViking MCP，但不取代 HTTP/SDK 主链路。 |
| Skill | 当前按会话注入 Markdown 规则。 | 可与 OpenViking 的 Skill 空间协同，但仍只作为文本规则。 |

## 十一、安全与运维要求

### 11.1 访问安全

- OpenViking Server 部署在内网或受控网络，不直接暴露公网端口；
- 远程访问使用 HTTPS、身份认证和用户隔离；
- 资源访问必须结合组织、部门、项目和角色权限；
- Electron 渲染进程不保存 OpenViking 服务密钥；
- 主进程记录服务调用、资源 URI、用户和结果摘要。

### 11.2 数据安全

- 原始文件、解析文本、摘要、向量和访问日志分别设置保留策略；
- 敏感资源发布前经过审核，必要时脱敏或分区存储；
- 个人记忆默认用户隔离，不自动写入组织共享空间；
- 资源删除或失效后，应同步处理索引和缓存；
- 备份恢复必须同时覆盖内容层和向量索引层。

### 11.3 许可证

OpenViking 开源主项目采用 AGPL-3.0。若作为独立服务部署，仍应由项目负责人和法务评估服务部署、源码修改、对外分发和商业交付中的许可证义务。

## 十二、部署与配置建议

### 12.1 开发环境

OpenViking 官方示例要求 Python 3.10 或更高版本，可在本机创建虚拟环境并启动服务：

```powershell
py -3.10 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install openviking --upgrade
openviking-server init
openviking-server doctor
openviking-server
```

令旗启动后轮询：

```text
http://127.0.0.1:1933/health
```

服务未就绪时，客户端应显示“上下文服务不可用”，但不应阻断普通聊天和本地工具能力。

### 12.2 生产环境

生产部署建议将 OpenViking Server 独立部署在企业内网、专用主机或容器环境中，并配置：

- HTTPS 或内网安全通道；
- 用户认证、组织隔离和资源 ACL；
- Embedding 与模型服务配置；
- 内容、索引和配置的备份策略；
- 服务健康检查、容量监控和检索延迟监控；
- 资源导入队列和失败重试。

## 十三、实施路线

### 阶段一：基础联通

在 Electron 主进程增加 OpenVikingClient、服务地址配置、健康检查、超时和错误提示。此阶段只验证服务可连接，不改变现有聊天流程。

### 阶段二：资源导入与检索

增加共享资源导入任务，将项目文档和业务资料批量导入 OpenViking；在 Agent 请求前召回摘要，按需读取详细内容。

### 阶段三：组织权限

增加用户、部门、项目、资源目录和发布审核模型，确保“可检索”与“可读取”都经过权限判断。

### 阶段四：记忆和协同

增加会话提交、记忆抽取、个人记忆与组织记忆分离，以及资源版本和审计能力。

### 阶段五：服务化交付

根据客户规模选择中心服务、私有化部署或混合模式，完善安装包、升级、备份、监控和许可证合规流程。

## 十四、后续规划

- 长上下文压缩、摘要和关键消息保留；
- OpenViking 资源导入、检索和读取的自动化测试；
- 共享资源的审核发布和完整审计日志；
- 组织级、项目级和个人级记忆策略；
- 更多本地文件和企业系统连接能力；
- 网络失败自动重试和断线恢复；
- 多窗口会话同步；
- 更完整的敏感数据识别、脱敏和访问告警。

## 十五、总结

令旗桌面客户端和 OpenViking 的合理关系是：

> 令旗负责与人交互、理解任务、编排 Agent、执行工具和控制权限；OpenViking 负责集中管理上下文资源、共享知识、语义检索和长期记忆。

因此，面向多人共享知识库的正式方案，应优先采用独立 OpenViking Server，并以“中心共享 + 用户隔离”的方式管理资源。桌面端可以连接本地伴随服务，但不应把 OpenViking 内部存储直接嵌入 Electron。

**用桌面 Agent 连接本地工作，用共享上下文连接组织知识，让每个人都能在安全边界内高效完成工作。**
